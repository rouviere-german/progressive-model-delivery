# Model card: churn-risk (demo models)

Format after Mitchell et al., "Model Cards for Model Reporting" (FAT* 2019). Every number below was
copied from the output of

```bash
uv run progressive-model-delivery bootstrap --root var/models
```

on Windows 10, Python 3.12.14, LightGBM/scikit-learn as locked in `uv.lock`. Training all six
models takes a few seconds on one CPU core.

**Read this first.** These models exist to be *rolled out*, not to be used. They are LightGBM
classifiers on a synthetic customer population, built so that specific failure modes exist for the
release system to catch. Nothing here says anything about real churn prediction. A per-release card
is also generated and stored content-addressed in the registry, and its digest is pinned inside the
signed manifest.

## Model details

- **Name:** `churn-risk`, six releases: `champion`, `better`, `identical`, `worse`,
  `subgroup_worse`, `feature_order_bug`
- **Type:** LightGBM binary classifier (gradient-boosted trees)
- **Owner:** Rouviere German
- **Date:** 2026-09-27
- **License:** MIT (code and generator; there is no third-party data)
- **Artifact format:** LightGBM **text**, never pickle. The repository has no pickle-family import
  and a test fails the build if one appears.
- **Release identity:** `release_id = SHA-256(canonical JSON of the manifest)`, Ed25519-signed. The
  manifest pins the model text digest, the version record digest, the run manifest digest, the model
  card digest, the dataset digests, the feature order and the PSI reference distributions.
- **Run manifest:** seed, dataset SHA-256s, package versions, training parameters and holdout
  metrics, recorded per release.

## Intended use

- **Primary use:** exercising progressive delivery. Each release is a scenario: a baseline, a
  genuine improvement, an A/A control, and three regressions of different shapes.
- **Intended users:** anyone reading this repository or running its demo, benchmarks or tests.
- **Out-of-scope uses:** any decision about any real person. The training data is generated by
  `models/synthetic.py`; it describes no one.

## Training data

- **Source:** `src/progressive_model_delivery/models/synthetic.py`, seeded. A customer population
  with six numeric features plus `region`, and a known label model with a region-specific
  interaction: in `south` the sign of `usage_trend`'s effect reverses. That interaction is what
  makes a subgroup-only regression possible at all.
- **Size:** 20,000 training rows, 8,000 holdout rows for the demo pipeline.
- **Fingerprint:** train `029fa858855371879ba9c924302d6c7eb2eb4bc0bef2abce70123dc473678726`,
  holdout `b80a3a934b61dae757974485f6a00070c01ba600ebf1a77221715f28fe20b65b` (stable across runs;
  both digests are pinned in every release manifest).
- **Contract:** pandera schema built from the same `FeatureSpec` table the generator, the pydantic
  request contract and the model feature order use, so the four cannot drift apart. Rows failing
  the contract are rejected, and the failure report names column, check and count -- never a value.
- **Region shares:** `north` 40%, `south` 12%, `east` 28%, `west` 20%. `south` is deliberately the
  smallest interesting subgroup: a regression there is hard to see globally.
- **Known gaps:** no time dimension, no seasonality, no concept drift over time, no missing values,
  no label noise beyond the generator's own Bernoulli draw.

## Evaluation

Two views of every release, because the difference between them is the point of this repository:

- **pipeline** -- scored on the validation frame the training pipeline prepared *itself*, bugs
  included. This is what the signed manifest records, and what an offline gate would see.
- **live** -- scored on the clean holdout, which is what serving actually sees.

For a healthy release the two agree. For a release with a pipeline bug they do not.

| Release | view | error rate | log loss | AUC | Brier | error `south` |
|---|---|---|---|---|---|---|
| `champion` | pipeline = live | 0.1254 | 0.2908 | 0.8889 | 0.0892 | 0.1753 |
| `better` | pipeline = live | 0.1114 | 0.2573 | 0.9128 | 0.0798 | 0.1340 |
| `identical` | pipeline = live | 0.1254 | 0.2908 | 0.8889 | 0.0892 | 0.1753 |
| `worse` | pipeline = live | 0.1594 | 0.3767 | 0.8278 | 0.1154 | 0.2138 |
| `subgroup_worse` | **pipeline** | 0.1124 | 0.2571 | 0.9126 | 0.0793 | **0.1307** |
| `subgroup_worse` | **live** | 0.1232 | 0.2859 | 0.8929 | 0.0879 | **0.2196** |
| `feature_order_bug` | **pipeline** | 0.1114 | 0.2573 | 0.9128 | 0.0798 | **0.1340** |
| `feature_order_bug` | **live** | 0.1915 | 0.6337 | 0.5963 | 0.1567 | **0.2565** |

Read the last four rows carefully:

- `subgroup_worse` was trained with **stale labels for the `south` region** (labels drawn without
  the region interaction). Its own validation frame carries the same staleness, so offline it looks
  slightly *better* than the champion everywhere, `south` included (0.1307 vs 0.1753). Live, its
  `south` error is **0.2196 against the champion's 0.1753** -- 4.4 points worse for 12% of
  customers -- while its global error (0.1232) is still *better* than the champion's (0.1254). No
  global metric, offline or online, would stop this model. The worst-subgroup guardrail does, during
  the shadow stage, before it serves anyone.
- `feature_order_bug` was trained with two feature columns swapped. Offline it is indistinguishable
  from `better` because the validation frame is swapped the same way. Live its AUC collapses to
  0.596. This is caught twice over: by signature verification, since the parsed booster's feature
  names no longer match the manifest's order, and by the guardrails if it were somehow loaded.

Metrics and why: **error rate** because it is the guardrailed decision quality; **log loss** as a
proper score, which catches calibration moves the error rate misses; **AUC** and **Brier** for
context; **error rate per region** because that is where the interesting failure hides.

The `identical` release is byte-identical in model text to the champion and exists so the A/A
validity study in `bench/bench_validity.py` measures a genuine null.

## Robustness and adversarial tests

The adversary here is a bad model reaching customers, so "robustness" means the release system's
robustness, not the model's.

- **Tampered artifacts:** `tests/integration/test_registry_release.py` -- unsigned releases,
  untrusted signing keys, tampered manifests, re-signed tampered manifests, tampered model bytes
  (rejected *before* parsing), non-LightGBM artifacts, and manifest/booster feature-order mismatch.
- **Deserialization:** `tests/unit/test_ml_serialization.py::test_pickled_npz_files_are_refused_on_load`
  and `tests/unit/test_no_pickle.py::test_source_tree_has_no_pickle_family_serialization`.
- **Metric poisoning:** `tests/integration/test_router.py::test_feedback_integrity` -- labels for
  unknown request ids, outside the maturation window, or submitted twice.
- **Fault injection:** `tests/integration/test_shadow_isolation.py` -- a challenger that crashes,
  hangs or errors must not change a single champion response.
- **Distribution shift:** `tests/integration/test_controller.py::test_a_covariate_shift_stops_the_rollout_from_advancing`
  -- a covariate shift holds the rollout instead of letting a verdict stand on traffic the model
  was never trained for.
- **Statistical adversary:** `bench/bench_validity.py` treats "an operator who looks at every pass
  and acts on it" as the adversary and measures the resulting false-decision rate.

## Drift and monitoring

- **Feature drift:** PSI per numeric feature against the champion's own training reference, which
  the signed manifest pins. Threshold 0.2, from 500 matured samples. A breach **blocks advancement**
  rather than triggering a rollback: drifting traffic makes the evidence untrustworthy, it is not
  itself evidence of harm.
- **Score drift:** PSI of the challenger's scores against its own holdout reference, threshold 0.25.
  This one *can* roll a rollout back on its own, because it needs no labels and so fires hours
  before the guardrails can. It trades precision for speed and has no error guarantee; that is
  stated in `docs/ROLLOUT_POLICY.md`.
- **Performance monitors:** `app_predictions_total{release,arm}`,
  `app_prediction_latency_seconds{release,arm}`, `app_prediction_errors_total{release}`,
  `app_e_value{guardrail,test}`, `app_feature_psi{feature}`, `app_score_psi`. Names and label sets
  are pinned by `tests/unit/test_observability.py`.
- **Retraining trigger:** out of scope. This repository decides whether a *given* candidate ships;
  nothing here decides when to train one.

## Ethical considerations

The data is synthetic and describes no real person, so there is no privacy question about the
training set itself. Two things are worth stating anyway, because they transfer to a real
deployment:

- **The subgroup guardrail is not a fairness control.** It detects that a challenger regressed for
  a group relative to the champion. A model that has always been worse for `south` passes every
  guardrail here, because both models are equally bad. Fairness is a question about the champion,
  and this system does not ask it.
- **Only the subgroups in the data contract are watched.** Here that is `region`. A regression along
  an axis the contract does not carry is invisible. Choosing those axes is a decision with
  consequences, and it is made outside this system.

Feature values are written to the prediction log because the drift monitor needs them. In a real
deployment that log is sensitive data with a retention policy; subject identifiers are HMAC-hashed
before anything is written, but the features are not.

## Caveats and recommendations

- Model quality numbers above are properties of a synthetic generator. They do not transfer.
- `identical`'s A/A role depends on byte-identical model text. Retraining with a different LightGBM
  version would change the artifact and the release ids, though the seeded metrics are stable.
- The pipeline/live gap that makes `subgroup_worse` interesting is *constructed*. Real stale-label
  bugs are usually messier and may be smaller, in which case the power study's 87.5% detection rate
  is the number to look at rather than the demo's certainty.
- The demo trains on 20,000 rows for speed. Guardrail behaviour depends on traffic volume and label
  maturation, not on training set size, so this does not affect the rollout claims.
